#45 的分组合并需两个匹配行，是带 PK/FK 条件的静态机制分析；本轮实测验证 N=2 构造，未做穷举最小性证明。最后一个 #1526 构造是辅助机制分解，不能据此宣称原查询必需 N=3。文本、超大整数、非法日期虽然符合源 DDL，却没有被认证为业务上合理的值。官方原数据库的反例及其最小性仍未知。#1490 本轮未执行，其结论仍停留于 18 包的静态推导。

独立验证脚本在全新内存数据库重建完整源 schema 和所有存储行，自行核对列、SQLite 存储类型、NULL、显式 NOT NULL、PK/UNIQUE、FK、integrity，再执行冻结原 SQL。原 `INT PRIMARY KEY` 不擅自强化成 NOT NULL；完整记录见 `replays.json` 和 `review_local/independent_validation.json` 的 replays 段。

COUNT(*) 直接使用真实 ExpressionEncoder 和 AST 类，覆盖 bound=0/1/2、所有删除掩码、无 FILTER / TRUE / FALSE / NULL，共 28 项。原语句位于 FILTER 条件内部，导致无 FILTER 的非空输入返回 0；bound=2 且有 FILTER 的 AST 又含 Bool+Bool。`COUNT_STAR.patch` 只把一条 append 移出条件，并写成整数指示 `If(Not(deleted), Int(1), Int(0))`。补丁仅在内存副本测试，属于工程修复候选，不计创新。

执行分两段：首段 0.100048125 秒，SQLite 两套回放成功，但额外 SQLParser 导入请求后台监控线程，被单线程守卫阻止，COUNT 未开始；独立 COUNT 又因补丁尚未生成而失败。原顶层 FAILED 和两个错误完整保留。补完段去除非必要 parser 导入，只完成 COUNT 作者/独立单测，用时 0.049894166 秒，没有重跑八个候选。两段累计实际执行墙钟 **0.149942291 秒**，准备和审核时间不算实验执行时间；这不是一个连续批次。每段结束线程数为 1，未启动子进程或求解器，进程峰值 RSS 约 54 MiB。

原计划的“连续单批”比用户“总 60 秒、一线程”更严格，修订记录在 `COMPLETION_NOTE.zh.md`。首段 369 项和补完段 378 项冻结 hash 全部一致。补完 freeze 未包含旧 ATTEMPT_STARTED；未事后改写 freeze，而根据冻结控制器的确定 JSON 序列化重建旧 marker，逐字节匹配，明确只作事后保全验证。详见 `POST_EXECUTION_PRESERVATION.json` 及独立审核。

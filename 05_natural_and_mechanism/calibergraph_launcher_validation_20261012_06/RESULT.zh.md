实际执行命令为 `/opt/homebrew/bin/python3.12 -I -S -B calibergraph_launcher_validation_20261012_06/validate_launcher.py`。只启动两个依次运行的轻量自有子进程：一次设置自身资源限制与锁验证；一次纯等待，以验证父进程超时终止和回收。未导入 SQLGlot、Z3、ParSEval 或任何数据库，SQL/solver/disprove 均为 0。工程检查不是科学重试。

## 已实施并实际验证

- 使用 v2 指定的 canonical runtime 路径、稳定锁文件和非阻塞 `flock`；锁描述符经 `pass_fds` 显式传给子进程。子进程重新打开同一锁文件的独立争用被拒，继承描述符的 inode 核对一致。
- 启动前持久化排他创建工程一次性记录，第二次创建收到 `FileExistsError`。该记录不会自动清除；它不是科学 `ATTEMPT_STARTED`。
- 父进程只持有一个自有 `Popen` 子进程，不使用全系统进程列表、旧 PID 或进程名清理。设置并读回 worker `RLIMIT_CPU=(60,60)`；不消耗 60 CPU 秒测试极限。
- 内存检查子进程约 0.072 秒退出，正常回收。纯等待子进程在 0.25 秒 deadline 触发终止，实际约 0.258 秒、退出码 -15，确认回收。这里验证的是超时路径，不冒称实际运行了 60 秒科学任务或承诺毫秒级绝不超时。

## 确定的当前技术阻塞

固定 Python 3.12.13、Darwin kernel 24.0.0 中，在科学库导入前执行 `resource.setrlimit(resource.RLIMIT_AS, (1073741824,1073741824))`，得到 `ValueError: current limit exceeds maximum limit`。前后 `getrlimit` 都为 `(9223372036854775807,9223372036854775807)`，所以此候选保护未生效。此进程报告的自身峰值 RSS 当时仅 10,928,128 字节；失败不能解释成“RSS 已超过 1 GiB”。Python 错误未提供 errno；本轮不推断内核精确拒绝原因，也不将其写成沙箱权限拒绝。

`RLIMIT_RSS == RLIMIT_AS` 已由本进程验证，因此改常量名不构成另一个可用限制。旧代码的自身 `ru_maxrss` 采样可以检测已发生的超限，但不能保证不超冲；`RLIMIT_DATA`、求解器内部限额又不能覆盖整个 Python/SQLite/Z3 worker。当前允许且已经检查的机制**不能认证 1 GiB worker RSS 硬预算**。这一结论针对当前环境与机制，不声称所有 macOS 环境或所有系统 API 都绝对不可能。

还未验证父进程意外死亡后的孤儿终止、完整科学库无派生进程路径、实际科学预算耗尽。锁和持久记录可防本协议异常后再次启动，但不能自行终止孤儿。内存准入失败后不继续这些科学运行前验证，也不以修复名义放宽预算。

## 具体下一步

1. 若必须保持“1 GiB 绝不可超过”：在已经允许、具备内核强制内存预算的隔离执行环境中验证并运行相同冻结输入；本轮没有证明这样的环境现成可用，也未安装、创建、购买或迁移任何环境。仅开放 `ps` 不能解决硬预算。
